## 1. Eval Agent（预测复盘）——采纳，高价值

### 1.1 现状缺口

- 回测（simulator._backtest）只给一个命中率数字，没有逐场明细，没有比分误差，没有概率校准分析
- 赛前预测没有独立留档：目前要靠 git 历史考古才能还原"当时预测了什么"（已人工做过一次 16 强复盘，流程应产品化）
- 推理文本从未被检验："模型说因为 X 所以 Y"，X 到底应验了没有，无人回看

### 1.2 职责与产出

新模块 `backend/agent/evaluator.py`，两个入口：

**（A）预测留档（每次 pipeline 运行时自动执行）**

每次生成 prediction.json 后，把所有"未赛场次"的预测快照追加到 `backend/data/prediction_ledger.jsonl`（一行一条：match_id、双方、预测比分/晋级方/p_advance、推理文本摘要、生成时间、模型参数版本）。同一场多次预测都留（赛程推进会更新预测），复盘时取**开赛前最后一条**。账本随仓库提交——彻底摆脱 git 考古。

**（B）复盘评估（比赛完赛后自动执行 / 手动 `python -m agent.evaluator`）**

对每场"账本中有赛前预测且已完赛"的比赛输出逐场明细 + 汇总：

| 维度 | 指标 |
|-----|------|
| 结果层 | 晋级方命中；比分全中；净胜球误差；总进球误差 |
| 概率层 | 该场预测概率的对数损失、Brier 分；按置信度分桶的校准表（如 50-60% 桶的实际命中率应≈55%） |
| 推理层（Qwen） | 把赛前推理文本 + 实际赛果/过程摘要喂给 qwen-plus：判定推理中引用的关键因素是否应验（如"体能优势"一方是否后程进球）。无 key 降级为跳过，只做结果/概率层 |
| 汇总 | 滚动命中率、平均误差、校准偏差（模型整体过度自信/保守）、系统性偏差候选（如"总进球持续被低估"——已有此迹象） |

产出 `backend/output/eval_report.json` + API `GET /api/eval` + 前端第五个 Tab「预测复盘」（逐场对照卡片 + 校准曲线）。

### 1.3 为什么值得做

- 答辩最有力的素材是"我们敢晒每一场的赛前预测原文和对错"——留档账本使这一点可信、可审计
- 校准分析直接反哺 Evolution（§2）：发现系统性偏差才知道该进化什么

## 2. Evolution Agent（自我进化）——采纳目标，修正形态

### 2.1 用户原始设想

独立的 evolution agent，自我更新进化。

### 2.2 评审质疑（重要）

1. **参数级进化已经存在**：auto-refresh → 新赛果 → walk-forward 重校准 → 参数热加载（v1.3 起）。这就是"进化"的安全内核，不需要为它另立 agent。
2. **"自由进化"有实害**：让 LLM 自主改特征/权重/代码，(a) 概率层会被未经统计验证的改动污染——F3 的教训是连人类直觉设计的特征都会被 walk-forward 否决，LLM 拍脑袋的改动更不可信；(b) 演示不可复现，评委追问"为什么这个参数是这个值"时无法回答；(c) 90+ 场样本撑不起更大的假设空间，过拟合风险随进化自由度指数上升。
3. **样本节奏**：淘汰赛每天新增 2-4 场，进化频率天然受限——重型进化机制没有燃料。

### 2.3 修正后的形态：Evolution = 闭环编排器 + 可审计进化史

`backend/agent/evolution.py`，职责收敛为三件事：

**（1）进化闭环编排**（把现有散件串成显式回路）

```
新赛果落地（auto-refresh 检测）
   → Eval Agent 复盘（含校准偏差诊断）
   → 依据诊断决定动作：
       · 校准偏差超阈值 → 触发重校准（现有 calibrate，两阶段）
       · Eval 发现系统性偏差（如总进球低估）→ 将对应参数维度加入/调整搜索网格（白名单内）
       · 无异常 → 仅记录
   → 重跑预测 → 新预测自动进入留档账本（供下一轮 Eval）
```

**（2）进化日志 `backend/data/evolution_log.jsonl`**

每次进化动作一条：时间、触发原因（新增哪些赛果/什么偏差）、参数 before→after、log loss before→after、当轮预测的改变（冠军概率变化 Top3）。这是答辩的杀手素材：**一条可回放的"模型随赛事自我改进的时间线"**。

**（3）LLM 进化提案（仅提案，不自动执行）**

qwen-max 阅读 eval_report 汇总，产出自然语言"进化建议"（如"考虑对高海拔场次引入进球修正"），写入日志的 `proposals` 字段，**由人工决定是否采纳**——LLM 参与进化方向，统计门禁把守进化执行。

### 2.4 安全边界（硬约束）

- 进化只允许改 `model_params.json` 白名单参数（现有网格维度 + 显式加入的新维度），永不改代码
- 一切参数变更必须过 walk-forward 门禁（MIN_GAIN 阈值），否则回滚
- evolution_log 只追加不修改，保证审计完整性

## 3. 实施排期

| 里程碑 | 内容 | 依赖 |
|-------|------|-----|
| E1 | evaluator.py：预测留档账本（pipeline 挂钩） | 无，立即可做 |
| E2 | evaluator.py：结果/概率层复盘 + eval_report.json + /api/eval | E1（账本积累≥1轮赛事即可用；历史部分可从 git 历史一次性回填） |
| E3 | 前端「预测复盘」Tab | E2 |
| E4 | evolution.py：闭环编排 + 进化日志（重构 auto-refresh 调用链） | E2 |
| E5 | 推理层评估（Qwen 判因素应验）+ LLM 进化提案 | E2/E4，需 DASHSCOPE_API_KEY |

架构位置：Eval/Evolution 均在流水线之外的**元层（meta layer）**——消费 prediction/ledger/赛果，产出报告与参数变更，不侵入五模块流水线本体。
