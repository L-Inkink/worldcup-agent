# 球探 Agent（Scout）需求描述 v0.1（待确认）

> 配套文档：[02-系统架构.md](./02-系统架构.md)（现有流水线）、[04-特征工程路线.md](./04-特征工程路线.md)（特征分层原则）
> 状态：**需求草案，未实现**。本文档目的是把口头需求转成可评审、可排期的规格。

## 1. 背景与目标

当前 `Rating` 模块的实力评估只用了球队级别的宏观数据（Elo、FIFA 排名、近期状态、本届表现），完全不涉及球员个体、教练、以及人和人之间的配合关系。这些信息在真实预测中很重要（例如核心球员近期状态火热、新帅上任战术未磨合、锋线组合默契度高），但目前只有 `key_players.json` 里人工维护的伤停信息覆盖了极小一部分。

新增一个 **球探 Agent（Scout）**，职责是：通过网络搜索，为球队补充球员俱乐部近况、教练履历、以及"球员与教练/球员与球员的共同履历"三类信息，输出结构化数据，供现有 Reasoner（Qwen）在生成推理文本时综合参考，让解释更丰富、更有说服力——**不改变 Predictor/Simulator 的概率计算**。

这遵循 `docs/04` 里既定的原则：新特征先进解释层，验证有效后再考虑是否量化进评分层。

## 2. 本阶段范围界定（三个关键决策）

| 决策项 | 结论 |
|---|---|
| 与现有模型的融合方式 | **仅作为解释层输入**：Scout 产出的数据喂给 Reasoner 做 prompt 上下文，不进入 rating.py 的加权公式，不影响 p_win/p_champion 等概率数值。后续如证明有预测增益，再按 docs/04 的校准流程决定是否量化进评分层 |
| 采集范围 | **热门夺冠球队 + 关键人物**：① 球队范围 = 当前晋级到淘汰赛阶段、或蒙特卡洛夺冠概率排名靠前的 8-16 支球队；② 人物范围 = 每队搜集主教练 + 核心球员，核心球员按 **身价（Transfermarkt 市场价值）排序** 自动筛选，取全队身价 Top 6-10 名，同时做**位置平衡校验**——若身价榜前列扎堆在同一位置（如清一色攻击手），则在门将/后防/中场/锋线四大位置区各强制保留至少 1 名身价最高的球员补入，避免核心球员名单全是攻击手、缺失后防信息。不做 26 人全队普查。其余球队沿用现有球队级数据，不受影响 |
| 羁绊（Chemistry）定义 | **共同履历/默契**，即定量可核实的历史合作事实，具体拆成：①球员与教练：该教练执教球员所在俱乐部或国家队的时长、执教期间战绩（胜率/夺冠）；②球员与球员：同俱乐部搭档时长、位置是否互补（如边锋+边后卫、中场搭档）、是否曾共同获得重要荣誉。**不做**媒体舆情/更衣室关系的主观判断，避免搜索结果掺入不可核实的八卦信息 |

> **重要补充**：评审发现两类特征（本届累计黄牌停赛风险、本届首发阵容磨合稳定性）**不需要搜索**，可直接用现有 `bracket` 已赛数据在 `features.py` 计算得出，价值等级为 🟢🟢（最高）。这两项建议**独立于球探 Agent 立项，优先实现**，不必等 Scout 的搜索方案（第6节）确定后才能推进。详见 3.1(6) 与 3.4(2)。

## 3. 数据字段设计

### 3.1 球员数据 `player_profile`

字段分七组：基础信息、身价与转会、俱乐部赛季表现、伤病历史、国家队数据、**本届赛事表现（新增）**、**战术角色与定位球职责（新增）**。每张表新增「用途」列，标注该字段对 Reasoner 解释文本的价值等级：

- 🟢 **核心解释依据**：能直接支撑"为什么看好/不看好这场"的具体理由，是 Reasoner 应优先引用的字段
- 🟡 **背书素材**：让文本显得更权威、更有细节，但本身不构成推理理由
- ⚪ **尽力而为**：数据源覆盖率低，能采集到就用，缺失不影响主流程

**（1）基础信息**

| 字段 | 说明 | 示例 | 用途 |
|---|---|---|---|
| `player_id` | 球员标识（姓名+球队编码） | `ESP_yamal` | — （标识字段，无解释价值） |
| `name` | 姓名 | "拉明·亚马尔" | — |
| `position` | 位置（细分：GK/CB/LB/RB/DM/CM/AM/LW/RW/ST） | "RW" | 🟢 用于判断对位关系、位置平衡校验 |
| `age` | 年龄 | 19 | 🟡 年轻/经验丰富的叙事素材 |
| `club` | 现俱乐部 | "巴塞罗那" | 🟡 背书素材 |

**（2）身价与转会 `market_value`**（核心球员筛选依据）

| 字段 | 说明 | 示例 | 用途 |
|---|---|---|---|
| `market_value_eur` | 当前市场身价（欧元，Transfermarkt） | 200000000 | 🟡 用于筛选核心球员名单，本身不构成比赛理由 |
| `market_value_date` | 身价评估日期 | "2026-06" | — |
| `market_value_trend` | 近1年身价走势 | "上涨"（较1年前 +€50m） | 🟡 侧面印证状态趋势，弱信号 |
| `peak_market_value_eur` | 历史身价峰值（可选） | 200000000 | 🟡 背书素材 |
| `transfer_history` | 转会记录列表（近3次） | `[{"date":"2023-07","from":"巴萨青训","to":"巴萨一队","fee_eur":0}]` | 🟡 背书素材 |

**（3）俱乐部赛季表现 `club_stats`**（近 3 个赛季，分位置给不同指标）

| 字段 | 说明 | 适用位置 | 用途 |
|---|---|---|---|
| `season` | 赛季 | 全部，如 "2025-26" | — |
| `appearances` / `minutes` | 出场次数 / 出场时间 | 全部 | 🟢 判断是否近期主力，比身价更接近"会不会打这场" |
| `goals` / `assists` | 进球 / 助攻 | 全部 | 🟡 基础背书数据，量大但因运气成分，解释力弱于 xG |
| `xg` / `xa` | 预期进球 / 预期助攻（若数据源可得） | 中前场 | 🟢 若能采集到，是比进球助攻更可靠的真实威胁水平信号；⚪ 覆盖率预期低于50% |
| `key_passes` | 关键传球（场均） | 中前场 | ⚪ 覆盖率预期低 |
| `shot_accuracy` | 射正率 | 前场 | ⚪ 覆盖率预期低 |
| `tackles` / `interceptions` | 抢断 / 拦截（场均） | 后卫/后腰 | ⚪ 覆盖率预期低 |
| `duel_win_rate` | 对抗成功率 | 后卫/中场 | ⚪ 覆盖率预期低 |
| `save_rate` / `clean_sheets` | 扑救率 / 零封场次 | 门将专属 | ⚪ 覆盖率预期低 |
| `penalty_save_rate` | 生涯点球扑救率（俱乐部+国家队） | 门将专属 | 🟢 淘汰赛点球大战概率不低，门将个人点球对抗历史具体、可搜索（新闻常提"点球扑救专家"），解释力强 |
| `penalty_saves_count` | 生涯点球扑救次数/被罚次数 | 门将专属 | 🟢 同上，支撑 `penalty_save_rate` 的样本量说明 |
| `yellow_cards` / `red_cards` | 黄牌 / 红牌 | 全部 | 🟡 背书素材（本届赛事内的累计黄牌见 3.1(6) 停赛风险，那个才是硬信号） |
| `data_source` | 该赛季数据来源URL | | — |

> 数据源建议：Transfermarkt（身价、转会、基础出场数据）+ FBref/WhoScored（细分技术统计，若可访问）。若某项指标搜索不到，字段留空，不强行捏造。标注为 ⚪ 的字段在实现验收时不作为硬指标，缺失不算失败。

**（4）伤病历史 `injury_history`**（近 1-2 年）

| 字段 | 说明 | 示例 | 用途 |
|---|---|---|---|
| `injuries` | 伤病记录列表 | `[{"type":"腘绳肌拉伤","start":"2025-11","end":"2025-12","days_out":34,"games_missed":7}]` | 🟡 背书素材，历史伤病≠当前状态 |
| `total_days_out_last_year` | 近1年累计缺阵天数 | 34 | 🟡 弱信号，仅作背景 |
| `current_status` | 当前状态 | "fit / doubt / out" | 🟢 直接关系到能不能出场，核心解释依据 |
| `risk_note` | 大赛前状态风险摘要，供 LLM 引用 | "近1年仅一次轻伤，大赛前状态稳定" | 🟡 背书素材 |

> 与现有 `key_players.json` 的 `status` 字段保持兼容，Scout 采集的 `injury_history` 可视为其详细版本来源。

**（5）国家队数据 `national_team_stats`**（与俱乐部数据区分开）

| 字段 | 说明 | 示例 | 用途 |
|---|---|---|---|
| `caps` | 国家队出场次数（总计） | 45 | 🟡 背书素材 |
| `nt_goals` / `nt_assists` | 国家队进球 / 助攻 | 12 / 8 | 🟡 背书素材 |
| `major_tournament_apps` | 参加过的大赛列表 | `["2022世界杯","2024欧洲杯"]` | 🟢 大赛经验是解释淘汰赛表现时最常被引用的角度 |
| `major_tournament_record` | 大赛表现摘要 | "2024欧洲杯4球3助攻，最佳新秀" | 🟢 同上，具体战绩比"参加过"更有说服力 |
| `debut_date` | 国家队首秀日期 | "2023-09" | — |

**（6）本届赛事表现 `current_wc_stats`**（新增，弥补原方案缺失——比赛季数据更贴题）

| 字段 | 说明 | 示例 | 用途 |
|---|---|---|---|
| `caps_this_wc` | 本届出场次数 | 4 | 🟢 判断是否本届首发常客 |
| `goals_this_wc` / `assists_this_wc` | 本届进球 / 助攻 | 3 / 1 | 🟢 本届状态，最贴近"这场比赛"的时间窗口 |
| `is_starter` | 本届是否常规首发 | true | 🟢 核心解释依据 |
| `yellow_cards_this_wc` | 本届累计黄牌数 | 1 | 🟢🟢 **停赛风险判断依据**——累计两黄将缺席下一场，是确定性事件，优先级最高 |
| `suspension_risk` | 是否存在停赛风险（累计黄牌达到阈值） | "一张黄牌预警，若下场染黄将停赛" | 🟢🟢 同上，建议独立于球探 Agent，用现有 `bracket` 数据在 `features.py` 直接计算，不依赖搜索 |
| `injury_status_this_wc` | 本届赛事期间是否有新发伤病中断 | "无" | 🟢 高时效性，需比其他字段更高频更新 |

> 停赛风险（`yellow_cards_this_wc`/`suspension_risk`）本质上不需要搜索——现有 `bracket` 数据里已含每场黄牌记录，可以在 `features.py` 里直接统计计算，建议作为独立特征优先实现，不必等球探 Agent 的搜索方案定型。

**（7）战术角色与定位球职责 `tactical_role`**（新增）

| 字段 | 说明 | 示例 | 用途 |
|---|---|---|---|
| `role_description` | 在球队体系里的具体角色 | "自由后腰，负责串联攻防" | 🟢 比泛泛罗列数据更具体，配合教练战术标签使用解释力更强 |
| `set_piece_duty` | 是否主罚定位球/角球/点球 | "队内首席任意球主罚手" | 🟢 淘汰赛常见"定位球制胜"叙事，识别度高、可搜索性较好（新闻常提及） |

**（8）通用元信息**

| 字段 | 说明 | 示例 |
|---|---|---|
| `recent_form_note` | 近5场文字摘要（伤停/状态/连续首发） | "近5场4首发，2球1助攻" |
| `honors` | 荣誉摘要（可选，简短） | "2024欧洲杯冠军、2025金童奖" |
| `data_source` | 数据来源URL列表（汇总各分组来源） | `["https://..."]` |
| `fetched_at` | 采集时间 | ISO8601 |
| `confidence` | 数据可信度（high/medium/low，人工或规则判定：多源交叉验证=high，单源=medium，搜索失败降级=low） | "high" |

### 3.3 羁绊数据 `chemistry`

> **范围说明（重要）**：羁绊模块信号弱、抓取成本高、幻觉风险大，已降级为**小范围试点**——只覆盖蒙特卡洛夺冠概率排名前 3-4 支球队，每队人工指定 2-3 组最核心的搭档/对位关系（如中卫组合、锋线连线），不做核心球员两两组合的全量机械生成（原方案 8人→C(8,2)=28条/队 的规模不再采用）。

分三类，均要求"事实可核实、可追溯来源"：

**教练-球员羁绊 `coach_player_bond`**

| 字段 | 说明 | 用途 |
|---|---|---|
| `coach_id` / `player_id` | 关联双方 | — |
| `shared_tenure_months` | 共同经历月数（该球员在该教练带领的球队里的时长，国家队或俱乐部） | 🟡 背书素材 |
| `shared_context` | "国家队" 或 "俱乐部"（若教练同时带过该球员的俱乐部，两条都记） | — |
| `joint_record` | 共同期间战绩摘要，如 "带队18场14胜" | 🟡 背书素材，因果链弱（战绩好≠这场比赛信任度高） |
| `note` | 一句话摘要，供 LLM 直接引用，如 "德拉富恩特自2022年起长期倚重亚马尔，为其国家队处子秀主帅" | 🟡 叙事素材 |

**球员-球员羁绊 `player_player_bond`**（队内配合，试点范围内）

| 字段 | 说明 | 用途 |
|---|---|---|
| `player_id_a` / `player_id_b` | 关联双方 | — |
| `shared_club` | 共同俱乐部（若有） | 🟡 背书素材 |
| `shared_tenure_months` | 同俱乐部搭档月数 | 🟡 背书素材 |
| `position_relation` | 位置关系（如"边路走廊搭档""中场双核""锋线连线"） | 🟡 叙事素材，好用但难验证真实性 |
| `shared_honors` | 共同获得的重要荣誉（如有） | 🟡 背书素材 |
| `note` | 一句话摘要，供 LLM 引用 | 🟡 叙事素材 |

**跨队对位关系 `matchup_history`（新增，仅在确定对手后按需生成）**

| 字段 | 说明 | 示例 | 用途 |
|---|---|---|---|
| `player_id_a` / `player_id_b` | 对位双方（分属对阵两队） | | — |
| `matchup_type` | 对位类型 | "边锋 vs 边后卫" | 🟡 叙事素材 |
| `historical_note` | 历史交锋摘要（媒体报道中提及的对位记录） | "上次交锋被该边锋两次突破成功" | 🟡 叙事素材，媒体报道口径，需注明来源，不做定量校验 |

> 对位关系只在淘汰赛对阵确定后，针对已排定的下一场比赛按需生成（而非提前枚举所有可能对阵），可控性和时效性优于队内羁绊。

### 3.4 球队集体特征 `team_collective`（新增）

覆盖三类此前遗漏、但性价比较高的维度：阵容深度、阵容磨合度、环境因素。前两类建议优先实现，环境因素为可选试点。

**（1）阵容深度 `squad_depth`**

| 字段 | 说明 | 示例 | 用途 |
|---|---|---|---|
| `impact_substitutes` | 1-2 名历史上常以替补身份改变比赛的球员 | `[{"player_id":"ESP_xxx","note":"历史多次替补建功"}]` | 🟢 淘汰赛加时/连续作战时替补质量常是决定性因素 |
| `bench_depth_note` | 板凳厚度定性摘要 | "锋线替补匮乏，后防替补充足" | 🟢 核心解释依据，配合现有 `rest_days` 使用 |

**（2）阵容磨合度 `squad_cohesion`（建议独立于球探 Agent，用现有数据计算）**

| 字段 | 说明 | 示例 | 用途 |
|---|---|---|---|
| `back_line_stability` | 本届后防线首发组合是否稳定 | "四人组合连续4场未变动" | 🟢🟢 与停赛风险同级——可直接从现有 `bracket` 已赛场次首发数据统计，不依赖搜索，建议优先实现 |
| `midfield_rotation_count` | 本届中场首发轮换次数 | 2 | 🟢 轮换频繁可能暗示战术不稳定或伤病问题 |
| `starting_xi_changes_last_match` | 上一场对比本场的首发变动人数 | 1 | 🟢 变动小=延续性强，变动大=需要解释原因 |

> 该组字段本质上是"本届已赛场次首发名单"的统计衍生特征，和停赛风险（3.1节）一样不需要搜索能力，可以在 `features.py` 中直接计算，建议与停赛风险一并列为独立优先事项，不必等待 Scout 的搜索方案定型。

**（3）环境因素 `match_environment`（可选试点）**

| 字段 | 说明 | 示例 | 用途 |
|---|---|---|---|
| `referee_style_note` | 主裁执法风格摘要（场均黄牌/判罚点球倾向） | "该主裁场均黄牌数较高，判罚较严" | 🟡 对解释"这场是否容易出现争议判罚"有一定价值 |
| `home_crowd_advantage` | 是否存在"半主场"效应（东道主/球迷聚集地） | "美加墨世界杯，该场地墨西哥侨民众多，形同半主场" | 🟡 叙事素材，淘汰赛解说常用角度 |
| `climate_adaptation_note` | 气候/海拔适应摘要 | "球队多来自欧洲平原联赛，需注意场地高海拔适应" | 🟡 叙事素材；场地信息现有系统已有，理论上可不靠搜索计算，只有"哪支队更/不适应"这一判断需要背景知识 |

> 环境因素整体标注为 🟡，优先级最低，仅在前述维度都跑通后视精力再做，不纳入本次验收硬指标。

## 4. 采集方式

- 触发时机：在 `pipeline.py` 中，`Simulator` 产出蒙特卡洛夺冠概率之后、`Reasoner` 生成推理文本之前，插入 Scout 步骤（新模块建议命名 `backend/agent/scout.py`）。因为需要先知道"谁是热门夺冠球队"才能确定采集范围。**例外**：停赛风险（3.1(6)）与阵容磨合度（3.4(2)）不经过 Scout，直接在现有 `features.py` 中用 `bracket` 已赛数据计算，可独立排期、无需等待 Scout。
- 核心球员筛选：先拉取该队大名单的 Transfermarkt 身价数据，按身价降序取 Top 6-10 名；再做位置平衡校验（门将/后防/中场/锋线四区各至少 1 人，若身价榜前列未覆盖某区，则在该区内选身价最高的 1 人补入替换榜单末位）。教练固定为主教练 1 人，不筛选。
- 采集手段：调用 web 搜索工具（本环境当前用的 `WebSearch` 工具在此次可行性验证中报错不可用；实现阶段需确认后端实际可用的搜索方式，例如第三方搜索 API、或允许 `web_fetch` 访问的白名单站点）逐个球员/教练发起搜索，解析搜索结果摘要，用规则或轻量 LLM 调用做结构化抽取，落入上述字段（基础信息、身价转会、赛季表现、伤病历史、国家队数据、本届赛事表现、战术角色七组）。身价与转会记录建议优先查 Transfermarkt；技术统计（xG/抢断/扑救率等）建议查 FBref/WhoScored；点球扑救记录、定位球职责、阵容深度（impact substitute）建议查新闻报道摘要，这类信息通常以文字描述形式出现，比表格类技术统计更容易被搜到。若不可得则该字段留空，不臆造数据。
- 跨队对位关系（`matchup_history`）与环境因素（`match_environment`）为按需/低优先级采集：仅在淘汰赛对阵确定后针对下一场生成，不提前枚举全部可能对阵。
- 频率：不需要像比分一样高频刷新。建议每次大赛阶段更新一次（如小组赛结束进入淘汰赛时全量拉一次），或人工触发 `--refresh-scout` 命令行参数，不纳入现有 `AUTO_REFRESH_MINUTES` 的高频自动刷新（避免过多搜索请求）。身价数据本身更新较慢（Transfermarkt 通常按窗口更新），可与其他字段同频；但 `current_wc_stats` 中的伤病/停赛相关字段需要更高频更新（贴近赛程节奏），与独立计算的停赛风险、阵容磨合度保持同频。
- 容错：单个球员/教练搜索失败 → 该字段留空并标记 `confidence: "low"`，不阻塞整体流水线；Scout 整体失败 → Reasoner 降级为不带球探信息的现有 prompt（即当前行为），不影响主流程稳定性。

## 5. 与现有系统的接口设计

- **新增文件**：`backend/agent/scout.py`（采集与结构化逻辑）、`backend/data/scout_report.json`（落盘产物，纳入快照兜底机制，逻辑与 `tournament.json` 一致）
- **Reasoner 改造**：`reasoner.py` 读取 `scout_report.json`，在生成单场推理和冠军长文的 prompt 中，追加对应球队的教练/关键球员/羁绊摘要作为参考上下文；`prediction.json` 中每场的 `reasoning` 可选新增 `scout_context_used: true/false` 标记，便于前端/审计知道这场解释是否用到了球探数据
- **Pipeline 编排**：`Collector → Rating → (Predictor+Simulator) → Features → Scout → Reasoner`，Scout 位于 Features 之后、Reasoner 之前
- **不改动**：`predictor.py`、`rating.py`、`simulator.py` 的计算逻辑和输出结构完全不变；API 契约不变（`scout_report.json` 暂不单独开 REST 路由，除非后续前端需要单独展示球探卡片）
- **测试**：新增 `tests/test_scout.py`，覆盖：单个球员/教练结构化解析的字段完整性、搜索失败时的降级行为、羁绊记录数量不超过 C(n,2) 上限、`confidence` 判定规则

## 6. 本次可行性验证结果（重要）

尝试在当前会话环境中用 `WebSearch` 工具试搜"某球员本赛季数据"和"某教练执教履历"，均报错：

```
tool type 'web_search_20250305' is not supported for this model
```

改用 `web_fetch` 直接访问搜索引擎，被网络白名单拦截（当前环境仅允许 `maragate.aibotplatform.com`）。

**结论**：球探 Agent 依赖的搜索能力，在当前 Cowork 会话环境里不可直接验证。实现阶段需要先确认：① 生产部署环境（阿里云 ECS 容器）里能否访问外部搜索 API（如 Bing Search API、Serper、SerpAPI 等付费/免费额度服务）；② 是否需要为 `scout.py` 单独配置一个搜索服务的 API Key（类似现有 `DASHSCOPE_API_KEY` 的管理方式）。这是本方案落地前必须澄清的技术前提，建议列为实现前的 spike 任务。
